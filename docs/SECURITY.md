# وضعیت امنیت کابل‌وب

## بررسی چرخه فعلی (2026-11-12)

### نقاط قوت
- فقط کلید publishable در کلاینت (service_role هرگز در مخزن نیست)
- اجبار status=pending در تمام insertهای عمومی
- escapeHtml برای جلوگیری از XSS در رندر کارت‌ها
- بررسی isSafeHttpUrl برای لینک‌ها
- چک ادمین با ایمیل + RPC is_kabulweb_admin
- SQL RLS کامل آماده در docs/security_rls.sql (شامل جدول پیشنهادی security_events)
- Content-Security-Policy روی صفحات اصلی
- cooldown سمت کلاینت (۶۰ ثانیه) + honeypot مخفی در فرم ثبت آگهی
- سایت زنده و داده‌ها از Supabase بارگذاری می‌شوند

### اقدامات فوری مالک (بدون این‌ها امنیت کامل نیست)
1. اجرای کامل docs/security_rls.sql در Supabase SQL Editor (اگر هنوز انجام نشده) — این شامل ایجاد جدول security_events برای ثبت رویدادهای مشکوک است.
2. تأیید وجود دو حساب مدیر در Auth و تست دسترسی.
3. تست اینکه کاربر عادی نتواند رکوردهای غیر-approved را بخواند یا ویرایش کند.
4. بررسی منظم لاگ‌های Supabase Auth و API برای تلاش‌های مشکوک.
5. فعال‌سازی هشدارهای Supabase یا اتصال به ابزار مانیتورینگ خارجی در صورت امکان.

### محدودیت‌ها (صادقانه)
- سایت استاتیک روی GitHub Pages است. دفاع پیشرفته DDoS، WAF سمت سرور و مانیتورینگ خودکار ۲۴/۷ فقط در حد امکانات میزبان (GitHub) و Supabase ممکن است.
- Rate limiting قوی سمت سرور وجود ندارد (فقط سمت کلاینت + سیاست‌های Supabase/RLS).
- سیستم ثبت گزارش امنیتی خودکار فقط پس از اجرای SQL و پیاده‌سازی سمت کلاینت/سرور فعال می‌شود. در حال حاضر فعال نیست.
- دسترسی مستقیم به داشبورد Supabase از اینجا وجود ندارد؛ تغییرات دیتابیس باید توسط مالک اجرا شود.

### اقدامات این چرخه
- به‌روزرسانی مستندات امنیتی با وضعیت واقعی و تاریخ فعلی.
- آماده‌سازی پیشنهاد جدول security_events در SQL (برای ثبت رویدادهایی مثل honeypot trigger، تلاش‌های غیرمجاز).
- بررسی کد: honeypot، CSP، escapeHtml و URL check در حال حاضر فعال هستند.
- ایجاد شاخه security/cycle-2026-11-12 برای تغییرات امن و قابل بازگشت.

**هیچ‌وقت ادعا نمی‌کنیم سایت را به‌صورت ۲۴ ساعته محافظت می‌کنیم مگر سیستم مانیتورینگ واقعی، هشدار و دفاع خودکار فعال و متصل باشد.**
