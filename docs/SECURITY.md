# امنیت کابل‌وب (KabulWeb Security Audit)

**تاریخ بررسی:** نوامبر ۲۰۲۶  
**مسئول:** توسعه و حفاظت امنیتی پروژه

---

## وضعیت فعلی امنیت

### نقاط قوت
- فقط کلید **publishable** در کلاینت قرار دارد (`js/supabase.js`). هیچ `service_role` در مخزن نیست.
- طول فیلدها با `.slice()` محدود شده است.
- استفاده از `escapeHtml` هنگام رندر کارت‌ها برای جلوگیری از XSS.
- بررسی `isSafeHttpUrl` برای لینک‌ها.
- وضعیت رکورد در insert همیشه اجباری `pending` است.
- پنل مدیر: کنترل دوگانه (allowlist ایمیل + RPC `is_kabulweb_admin`).
- فایل `docs/security_rls.sql` آماده است و سیاست‌های RLS مناسب را تعریف می‌کند.

### نقاط ضعف / ریسک‌ها
1. **RLS هنوز در Supabase اجرا نشده** (مطابق STATUS.md). بدون اجرای فایل SQL، امنیت پایگاه داده ناقص است.
2. سایت استاتیک روی GitHub Pages هیچ حفاظت سمت سرور برای DDoS، bot، یا rate limiting ندارد.
3. هیچ سیستم ثبت گزارش امنیتی (security events log) وجود ندارد.
4. هیچ Content-Security-Policy فعال نیست (به دلیل وجود inline script).
5. فرم‌ها فقط اعتبارسنجی کلاینت دارند؛ حمله به Supabase برای spam ممکن است.

---

## اقدامات فوری لازم (مالک پروژه)

1. **اجرای حتمی** فایل `docs/security_rls.sql` در Supabase SQL Editor.
2. تست ورود مدیر و رد شدن کاربر عادی.
3. فعال‌سازی Cloudflare (یا سرویس مشابه) جلوی GitHub Pages برای حفاظت DDoS و bot.
4. فعال کردن Supabase Auth rate limits و بررسی لاگ‌ها.

---

## پیشنهادات تقویت

- ایجاد جدول `security_events` برای ثبت تلاش‌های مشکوک (در نسخه بعدی).
- افزودن اعتبارسنجی قوی‌تر تماس (شماره/ایمیل).
- محدود کردن تعداد ارسال فرم در بازه زمانی کوتاه (کلاینت + Supabase).
- مراجعه منظم به لاگ‌های Supabase Auth و Database.

**یادآوری:** حفاظت ۲۴ ساعته فقط زمانی ممکن است که سیستم مانیتورینگ خارجی (Cloudflare + Supabase Alerts) فعال و متصل باشد.
